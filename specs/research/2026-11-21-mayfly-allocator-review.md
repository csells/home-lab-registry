# Mayfly and the home-lab allocator

## Conclusion

Use Mayfly as a reference for **worker provisioning and maintenance**. Keep the allocator as the authority for admission, lease ownership, recovery, and destructive cleanup. Mayfly manages a declared fleet of CI worker nodes. The separate ephemerd daemon claims GitHub jobs and runs their disposable execution environments. Our agents need an owned environment that can survive many tests, extend its lease for weeks, and recover work after deletion. GitHub Actions jobs could eventually consume a bounded lab pool through a CI adapter. ## Boundaries worth preserving

- **A fleet state file is a weaker authority than the pilot's transaction journal.** Mayfly writes local YAML using a temporary file and rename. In its provision path, clone and subsequent startup can precede appending and saving the member record. Its refresh walks already-recorded members. The code therefore leaves a crash window where a new guest can exist outside that record. The dynamic Proxmox slice should test a crash immediately after the provider accepts a clone, then prove exactly one owned guest, no duplicate disks, and no admission until the outcome is resolved. [State persistence](https://github.com/ephemerd/mayfly/blob/478f095d84315c893ac131537d2678c7ba78e40a/internal/state/state.go#L176-L225) · [Provision sequence](https://github.com/ephemerd/mayfly/blob/478f095d84315c893ac131537d2678c7ba78e40a/internal/engine/apply.go#L123-L242) · [Recorded-member refresh](https://github.com/ephemerd/mayfly/blob/478f095d84315c893ac131537d2678c7ba78e40a/internal/engine/refresh.go#L78-L157)
- **A failed lookup or drain does not settle ownership or data disposition.** Mayfly's destroy path drops a member on a lookup error and treats drain and shutdown as best effort. Its idle wait can proceed after failed probes or a timeout. That is a policy choice for replaceable CI capacity. Our destructive path needs verified identity and either a recoverable checkpoint or the owner's explicit discard decision. Show unreachable, confirmed absent, active, held, and eligible for reclamation as distinct states. [Member destruction](https://github.com/ephemerd/mayfly/blob/478f095d84315c893ac131537d2678c7ba78e40a/internal/engine/apply.go#L274-L302) · [Drain behavior](https://github.com/ephemerd/mayfly/blob/478f095d84315c893ac131537d2678c7ba78e40a/internal/engine/graceful.go#L172-L219)
- **Keep CI scheduling separate.** Ephemerd has a real queue and transient retry system. Its slot implementation documents a capacity leak where slow VM teardown delayed slot release. For lease admission, reject requests immediately when capacity is unavailable. Track compute that is actually free independently from disk, backups, and guest identity still held for cleanup. A cleanup failure can release verified CPU and memory without returning the old disk or slot to service. [Retry queue](https://github.com/ephpm/ephemerd/blob/2b0c262955e92fbfcb3fbd901c841c99283ac942/pkg/scheduler/retry_queue.go#L1-L31) · [Slot failure analysis](https://github.com/ephpm/ephemerd/blob/2b0c262955e92fbfcb3fbd901c841c99283ac942/pkg/scheduler/slots.go#L15-L40)
- **Use stronger identity and supply-chain checks before adopting patterns.** Mayfly's Linux template path reuses images by filename and does not explicitly verify a digest in that download code. Its Mac enrollment supports trust on first use. Its worker bootstrap renders GitHub App material into user-data for the runner host. In our lab, pin trusted host identity independently, verify image provenance, and scope guest credentials to the task. Wrapper, image, and cloud-init material belong on the provider side of that trust boundary. [Image staging](https://github.com/ephemerd/mayfly/blob/478f095d84315c893ac131537d2678c7ba78e40a/internal/pve/template.go#L104-L138) · [Download path](https://github.com/ephemerd/mayfly/blob/478f095d84315c893ac131537d2678c7ba78e40a/internal/pve/template.go#L234-L251) · [SSH first use](https://github.com/ephemerd/mayfly/blob/478f095d84315c893ac131537d2678c7ba78e40a/internal/engine/sshtransport.go#L149-L180) · [Bootstrap inputs](https://github.com/ephemerd/mayfly/blob/478f095d84315c893ac131537d2678c7ba78e40a/internal/engine/apply.go#L136-L181)
- **Evaluate Windows from the build recipe, not the platform table.** The repo has a Windows Server 2025 Packer recipe and Cloudbase-Init build and bootstrap scripts. That is a starting point for a versioned Windows worker image. It does not demonstrate our intended Windows editions, GUI checks, driver support, or desktop licensing. [Packer recipe](https://github.com/ephemerd/mayfly/blob/478f095d84315c893ac131537d2678c7ba78e40a/packer/windows/windows-2025.pkr.hcl) · [PowerShell guest bootstrap](https://github.com/ephemerd/mayfly/blob/478f095d84315c893ac131537d2678c7ba78e40a/internal/cloudinit/templates/user-data-windows.ps1.tmpl)

## Suggested acceptance sequence

1. Qualify one dynamically cloned Linux recipe against the real Proxmox host, keeping one allocation authority. Verify signed or digest-pinned inputs, storage and network preflight, actual guest access, interruption after clone acceptance, and exact cleanup after verified export. Exercise capacity rejection during replacement overlap.
2. Add a read-only change plan for worker and recipe maintenance. Work through one real update and one replacement, including a lost operation reply and an unavailable host. Show retained resources and a manual recovery path in the registry.
3. Validate a single Apple build recipe with host-owned provisioning and an explicit ownership manifest. Then evaluate GUI and simulator recipes independently. If there is demand for GitHub Actions, test ephemerd inside a delegated pool and prove its capacity accounting cannot oversubscribe the allocator.
